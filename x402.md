# Paid bars and request records

The existing `serve` and `anchor` commands can also serve `GET /paid/v1/bars`. Add a `paid` object to the node JSON described in [docs/NODE.md](docs/NODE.md). Omitting that object preserves the free-only configuration. A partial or invalid object stops startup with `paid route startup refused: invalid or missing configuration`. Validation happens before venue access. Install the dependencies in `requirements.txt`; `cryptography` verifies the public manifest signature and signs per-call CDP JWTs with P-256 or Ed25519. There is no payee signing operation.

The top-level `store_provider_id` identifies the store supplying bars. The `paid` object requires the fields below, choosing one authentication mode; no price, cap, recipient, facilitator or credential path is supplied by code.

| Field | Meaning |
|---|---|
| `price_usdc` | Positive decimal string, at most six decimal places; converted exactly to USDC atomic units |
| `daily_cap` | Positive integer count of paid requests per payer per UTC day |
| `payTo` | Operator's lowercase Base address, identical to the signed manifest's `payee` |
| `facilitator_url` | Facilitator base URL; `/verify` and `/settle` are appended |
| `facilitator_key_id` | CDP API key identifier; required with `facilitator_key_file` for CDP authentication |
| `facilitator_key_file` | File outside the source tree containing the CDP API key secret: EC P-256 PEM or base64 Ed25519 (32-byte seed or 64-byte seed plus public key); never put its contents in config |
| `credential_file` | Legacy alternative for fake checks: file outside the source tree containing the complete HTTP Authorization header value |
| `max_timeout_seconds` | Integer from 1 to 300 limiting authorization expiry |
| `origin` | Canonical public HTTPS origin advertised in the resource and manifest |
| `scope` | Manifest scope and per-use entitlement for bars |
| `serve_provider_id` | Serve provider identifier matching the manifest's `provider_id` |
| `meter_file` | Append-only local JSON-lines usage file |
| `ledger_file` | Separate append-only local JSON-lines replay and cap ledger |
| `manifest_file` | Supplied canonical signed commercial manifest, maximum 64 KiB |
| `envelope_file` | Supplied detached public signature envelope, maximum 1024 bytes |
| `manifest_pin` | Public pin object: `kid`, `type`, `address`, `publicKey` |

Configure both `facilitator_key_id` and `facilitator_key_file`, or only `credential_file`; incomplete or mixed authentication settings stop startup. Paths resolve relative to the configuration file. Ledger, meter, authentication, manifest, envelope, database and config paths must be distinct. Authentication contents are read only during each facilitator call, including separate reads for verification and settlement. The node does not read that file at startup or retain its contents in application state. The supplying system can replace it between calls.

CDP calls send `Authorization: Bearer <JWT>`. Each JWT has `alg` ES256 or EdDSA, `typ` JWT, the configured `kid`, and a fresh random header `nonce`. Claims are `sub` equal to the key identifier, `iss` equal to `cdp`, `nbf` equal to the current Unix second, `exp` exactly 120 seconds later, and `uris` containing only `POST <host><path>` for that call, including any port and base path. Verify and settle receive separate JWTs. The secret and parsed key leave local scope immediately after signing; the Authorization value leaves local scope after the call. Python does not guarantee secure erasure of immutable objects. Signing failures use a fixed error message and never include key text. Requests use a ten-second deadline, no redirects, no proxy discovery, no cookies and no retry loop. HTTPS is required except for a scratch facilitator at loopback ports 47000–47999. The HTTP exception also applies to the scratch manifest and is not a production wallet origin contract.

## Protocol

An unpaid request returns 402 with a JSON challenge and the same base64 JSON in `PAYMENT-REQUIRED`. This follows x402 v2 `exact`, Base `eip155:8453`, and the official six-decimal USDC contract. `amount` and `payTo` come from configuration. The signed manifest advertises the facilitator URL. `X-PAYMENT` and `PAYMENT-SIGNATURE` accept the v2 payload; conflicting or duplicate headers are rejected. Local checks cover the offered terms, address and signature encodings, nonce, and authorization time window. The facilitator verifies the signature; encoding checks alone do not establish payment validity.

The node calls `/verify`, requires `isValid: true` and the matching payer, then prepares a valid bars response and calls `/settle`. Only `success: true`, matching network and payer, a transaction hash, and a matching amount when present permit delivery. The response body uses the existing public bars handler, with the same decimal strings and provenance. Receipt headers are `PAYMENT-RESPONSE` and `X-PAYMENT-RESPONSE`. Paid responses use `Cache-Control: no-store`, including errors; OPTIONS supports browser payment headers. HEAD cannot settle. The three free routes `/public/v1/instruments`, `/segments` and `/public/v1/bars` continue without payment.

A process-wide asynchronous lock serializes paid admission and settlement. The ledger is exclusively locked for the process lifetime. A `pending` line is flushed before settlement; a `settled` or `failed` line follows a confirmed outcome. Payer addresses are normalized and paired with the UTC day captured when the request enters the middleware. Settled and pending reservations both consume the cap. At the cap, the node returns 429 before contacting the facilitator or reading bars. A confirmed rejection releases the slot, but every attempted nonce remains blocked against replay. A timeout, pending response, malformed settlement response or interruption retains the reservation, blocks replay and returns no bars. Restart reconstructs these decisions; invalid ledger content or a second process using the ledger stops startup. No timer advances the day or clears state.

Keep the ledger intact. Uncertain payments and settled payments with interrupted delivery require operator reconciliation; this version has no automated retry, redelivery or refund route. A write failure prevents paid delivery and further paid settlements. Appends are flushed to the operating system; power-loss durability is not guaranteed by a filesystem sync. The ledger grows without compaction and is loaded into memory on startup. Run one process per ledger.

## Signed manifest

`GET /.well-known/traderswift-manifest.json` returns the exact configured canonical UTF-8 bytes and `X-TraderSwift-Manifest-Signature`, the unpadded base64url encoding of the signature envelope. The body uses `traderswift.frontend-manifest.v1`: `schema`, `chain_id`, `subnet`, `provider_id`, `version`, `maker_name`, `origin`, `api_versions`, `scopes`, `licence`, `payee`, `network`, `asset`, `amount_atomic`, `terms`, `price_version`, `issued_at`, `expires_at`, `facilitator_urls`, `refund_contact`. Integers are strings. This node requires `timeseries`, `traderswift-1`, API version `2`, a single configured scope, and per-use terms with duration `0`. Validity is at most seven days and is checked again on each paid or manifest request.

Canonical keys use UTF-16 ordering; duplicate JSON keys, extra manifest fields, noncanonical bytes, stale validity, mismatched price, payee, origin, provider, scope or facilitator are rejected. The envelope is `{kid, address, pub_key: {type, value}, signature}`. Its public pin must match exactly; the public key type is `tendermint/PubKeySecp256k1`. The node checks the Cosmos address derived from the compressed public key and verifies a compact low-S secp256k1 signature over the standard ADR-36 document. Its signed data is `traderswift frontend manifest v1` followed by a newline and the canonical manifest bytes. Supply these public artifacts from the operator's external signing process. Provider registration and hub anchoring are not established by this local verification.

## Local rec.v1 records

With paid configuration enabled, one JSON line is appended for every application request, including free routes, errors, OPTIONS and the manifest. A successful GET returning bars or segments is `kind: bytes`; every other request is `kind: view`. Each flat value is a string. Fields are `schema: rec.v1`, `event_id` (random UUID), `ts` (request-arrival Unix milliseconds), `kind`, `node_id`, `resource` (allowlisted path, otherwise `other`), `status`, and `bytes` (response body byte count, zero for HEAD). A bytes record also carries `store_provider_id` and `serve_provider_id`. This counts prepared response bytes, not TCP acknowledgement or independently proven delivery.

The meter contains no payer, payment payload, signature, credential, raw query, client header or facilitator response. The separate payment ledger contains only `payment_id` (hashed network/asset/payer/nonce identity), payer, day and status. Access logging is disabled, facilitator errors are reduced to fixed messages, and receipt fields are allowlisted. A meter write failure returns 503 and disables further paid settlements. Requests rejected by the HTTP parser before entering the application cannot produce application meter records.

## Verification limits

The socket-free checks cover configuration, signatures, local validation, replay and cap recovery, UTC day rollover, file locking and the paid handler with a stub transport. A socket-free application check also exercises concurrent admission, route registration, free routes, manifest serving, meter counts and write failure. The integration check uses a fake venue and facilitator, synthetic payment addresses, a throwaway manifest signer and an external scratch Authorization marker. It exercises success, refusals, concurrent cap admission, restart, settlement ambiguity, free routes, meter counts and leakage checks.
